# 人工巡检方法

巡检回答一个问题：某个机制是否真的成立，而不是"有没有对应的文件或函数"。这份方法与具体包站号解耦，不预填任何包的结论。规范包清单与依赖见 [../requirements/INDEX.md](../requirements/INDEX.md)，覆盖缺口见 [../requirements/GAP.md](../requirements/GAP.md)，测试规则见 [AXIOMS.md](../requirements/verification-system/AXIOMS.md)。

## 一、三个判断分开做

每次核对按以下顺序，不先看实现替它找理由。

| 判断 | 要回答的问题 | 不接受的替代品 |
|---|---|---|
| 用户意志 → WHY / WHAT | 用户究竟需要什么后果？哪些限制是用户要的，哪些是工程师自加的？ | "现在就是这么写的"、"现有测试要求如此" |
| WHAT → 代码 / tests | 条款的判断与副作用由谁拥有？真实入口是否走到了它？ | 函数存在、注释提到条款、Surface 自己测得很漂亮 |
| 代码 → 真机体验 | 日用模型在真实 Host 中能否做对？失败时人能否理解并接手？ | 模型说"已完成"、mock 全绿、日志出现一个成功词 |

先请用户用一两句话说出本包希望保住的价值与不想付的代价，再与现行 WHY、WHAT 比较。没有直接用户裁决的地方标"设计待确认"，不把巡检建议包装成用户原话。

WHAT 是当前实现的验收合同，但不是拒绝用户修订产品的理由。用户不接受 WHAT 时，先确定修订，再同步 WHY、WHAT、代码和测试——不能只改测试让旧实现变绿，也不能先改代码把新行为偷偷变成既成事实。

### 每包固定读法

1. 读 WHY：删掉历史施工背景后，还能否说清它为何存在？它的代价是否值得？
2. 逐条读 WHAT：主体、触发、前提、允许后果、禁止后果、失败后果是否明确？硬阈值和永久限制有无用户依据？
3. 核对实现与测试：是否符合当前机制？关键函数、文件、测试文件还存在吗？有没有旧分支、空实现或绕行入口？
4. 沿真实入口追一条正向路径，再追一条失败路径，不止读 Surface。
5. 做最小现场场景：先普通成功，再一个有区分力的反例；涉及取消、未知后果或恢复时，再做对应边界。

## 二、保留真实机制，隔离真实损失

### 使用隔离的练习仓库

不要拿源码仓库、用户工作目录或正式远端做破坏性场景。建立独立 Git 仓库，用可丢弃的本地 bare remote 作为后期发布目标。worktree 可能共享 Git common directory 与插件持久化资料，不能只建同仓 worktree 就称完全隔离。

练习工程不需要业务复杂度。人预先确定需求与固定正反例；不要让同一个被测模型同时发明需求、写实现、改 expected 并宣布通过。

### 固定环境，不复制日常隐患

保存本次源码提交、构建或包版本、实际插件入口、Host 版本、路由配置版本与所用模型。使用独立 HOME 与 XDG 配置、数据、状态、缓存目录，只给这个 profile 配置获准的凭证；凭证不写进仓库，不打印整个环境变量表。

### 三种证据明确分开

- 真实 Host + 真实 provider + 自然任务：用于体验、可理解性与通常行为。
- 真实 Host + 受控故障端点：用于指定拒绝、延迟、重复和取消。
- 确定性测试：用于精确竞态与不变量。

三者各有用途，不互相冒名。模型自述"我读过规范""我没有重复执行"都不是证据；必要时核对实际工具记录、provider 请求、持久化事件、文件 diff 与进程退出。拿不到请求级观测，就不能宣布 prefix、horizon 或隐私隔离通过。

## 三、每段只保留一条锚定场景

不要审一包就重新跑完整世界。保存能快速说明这一段仍然成立的最短场景，只在该段相关能力改动时回归。

真机发现的产品缺陷，必须缩成包内正式自动回归，再修复、重跑对应现场。真人日志用于发现与说明问题，不是"只跑不提交的探针"替代正式证明。

不要预设所有包都能靠普通对话完整验证。故障注入、trace/prefix 比较、精确重复投递、容量竞争属于需专门证据的场景；缺条件就记清缺什么。

## 四、记录要轻，四项结论分开

每包一条短记录，放在该包现有审查说明或现有 GAP 体系；不另造清单数据库、统一打分系统或第二套 proof registry。原始日志不全文贴进规范。

一条记录至少回答：包 / 提交 / 入口角色；用户裁决（认可、修订、仍未决定）；实现核对（真实入口、判断属主、提交点、偏差）；现场证据（环境、请求标识、实际动作、结果、最短日志位置）；剩余与回归（未触发分支、收证位置、正式回归位置）。

分别回答"意志是否确认""合同是否自洽""代码是否贯彻""哪些场景已实测"。其中一项未闭合，不能用其它三项的绿色替它背书。

允许的结论：此范围已通过、发现缺陷、设计待裁决、环境阻塞、未实测。系统输出确定但证据不足应当算问题；模型输出不确定但系统诚实暴露也可能符合合同。

人工停止条件由人预先约定（费用与请求上限、受控并发规模、允许写入的目录/分支/远端、可终止的进程）。触及上限就停止并记录未完成，不把预算写成新的产品 hard gate，也不通过放宽时间、重复运行或临时关机制得到绿灯。

## 依据与导航

以下命令在仓库根运行。

- 单元套件：`node requirements/verification-system/tests/run.mjs`（自动发现 requirements/<package>/tests/ 下全部测试文件）
- 单包单文件：`node --test requirements/<pkg>/tests/NNN.test.mjs`
- 全静态门禁：`node scripts/check.mjs`
- 集成调度：requirements/verification-system/tests/integration/run.mjs
- Long Stroke e2e：requirements/verification-system/tests/014.test.mjs

验证按承诺与实际副作用选择 Pure、Temporal、Adapter 或 Long Stroke；只有共享物理生命周期本身是承诺时才使用连续场景。规则与入口见 [AXIOMS.md](../requirements/verification-system/AXIOMS.md)。
