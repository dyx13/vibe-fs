**本次只到**：可照做的实现流程。不实施。
**边界**：产品语义只由 `requirements/<包>/WHAT.md` 定义。本文只写「怎么做」。冲突时以规范与源码为准，并修正本文。
**基线**：写作时工作树含 `feat-PLANNER/` 与 `000.md`。动工前必须 `git status` 并重读当前源码。本文行号为写作时近似值。

## §0 记号

- 算法头：`Algorithm <字母>（<题目>）。输入…。输出…。`
- 步骤标号：字母加数字，如 `M1.`；子步 `M1.1.`
- 步骤名放方括号内，句尾用句号。赋值用 `←`。比较用 `＝`、`≠`。
- 条件句：`若…，则…。` 跳转：`转 M5.` 循环：`循环…，直到…。`
- 结束：`算法终止。` 或 `返回…。` 圆括号内是说明。`#` 开头是断言。
- `▷` 是裁决点。裁决必须留下书面结论与证据。
- 锚点格式：`<相对路径> · <符号>`（行号）。
- `[INFERENCE]` 标注推测，不是核实事实。

**名词固定**：work、任期（incumbency）、stage、state、review、deliver、接力、晋级、授权、自然停止、baton、LWR、P、U、DevOps 绑定、前缀重锚。
**动词固定**：读、写、跑、改、删、提交、推送、记录。

## §1 全局不变量

I1. 权威单一。产品语义只由 `requirements/planning/WHAT.md` 定义。计划、提案、本文都不增加义务。
I2. 规范先行。改代码前先读规范。合同变化时，先改 `WHAT.md`，再改代码与测试。
I3. 红先绿后。行为变化先有一条按新合同失败的测试。禁止先改代码再补测试。
I4. 手工编辑。禁止用自动化程序批量增删改源码。
I5. 原子闭环。一个工作包一次提交。提交内规范、代码、测试三者一致。
I6. 证据分级。实跑过的写「通过」。未跑过的写「未验证」。禁止把「预计红 / 绿」写成证据。
I7. 保护用户改动。动工前读 `git status` 与相关 diff。无关改动一律保留。
I8. 构建只用 `node scripts/build.mjs` 或 `npm run format-build-test`。严禁 `dotnet build`。
I9. 不削弱断言。不放大超时。不重跑撞绿。
I10. 非 Plan 路径行为字节不变。Manager 的 review 字节行为不变。
I11. 推送前先 `git pull --rebase`。严禁对 `master` 强制推送。
I12. 涉及行为、持久化、Host/provider、Git 或跨包边界时，跑对应 requirement 测试套件，尽量不全量漫跑。

## §4 目标状态

### 4.1 事实（durable 事件）

```text
保留  PlanWorkOpened(workId, root)
      PlanDevOpsBound(workId, devopsId, target)
      PlanIncumbencyOpened(workId, incumbencyId, stage, openingCursor)
改    PlanIncumbencyRetired(incumbencyId, outcome)      # outcome = Relayed | Delivered
改    PlanDelivered(incumbencyId, workId, digest, path, execSessionId)
新增  PlanReviewed(incumbencyId, stage, outcome)        # outcome = Promoted | Stayed
新增  PlanReopened(incumbencyId)
删    PlanAskPending / PlanAskResolved
```

- `PlanReviewed` 每任至多一条。`Promoted` 承载晋级。
- `PlanReopened` 清除投影里的 `Delivered`，保留 `Active`。
- `PlanDelivered` 记 `execSessionId`（起出的 Manager 会话）。

### 4.2 work 状态

```text
WorkId           : string option
Root             : string option
Active           : { Id; Stage; Phase; Authorized } option
Retired          : incumbencyId list
LatestRetirement : (incumbencyId, outcome, openingCursor, retirementCursor) option
BoundDevOps      : (devopsId, target) option
Delivered        : { Digest; Path; ExecSessionId } option
Reviewed         : (incumbencyId, outcome) option
PreviousIncumbencyStage : stage option
```

- `Authorized`：本任是否已获交付权（S3 的 review 空集置 true）。
- `PendingAsk`/`LatestResolvedAsk` 删除。

### 4.3 阶段与状态

```text
stage  = S1 | S2 | S3
state  = active | delivered
next(S1) = S2 ; next(S2) = S3 ; next(S3) = LAST   # LAST 即「授权交付」
```

- stage 只由 `PlanReviewed(Promoted)` 推进。
- state 由 `PlanDelivered` 进 delivered，由 `PlanReopened` 回 active。

### 4.4 工具面

| 工具 | 形态 | 作用 | 门 |
|---|---|---|---|
| `js-plan` | JS 编程面 | 读写 P：`read`/`edit`/`rewrite` | 单路径；无仓库能力 |
| `ask` | 编排面 | 同步委托固定 DevOps 只读（含 bash） | 有活跃任期；至多一个未决 |
| `review` | 编排面 | 与 manager 同 tool；Plan 目标 = 下一里程碑 | 硬门；每任一次 |
| `deliver` | 编排面 | 持权 → 交付；无权 → 接力 | 有活跃任期；无 blocker |

### 4.5 路径

```text
root   = <git-common-dir>/wanxiangshu
path   = root/plan/<workId>/plan.md
workId = plan 会话的 session id
```

### 4.6 提示词

- role law 常驻：`resources/provider/role/plan/{en,zh-CN}.md`，厚度对齐 engineer。
- stage 方法按任期追加：`resources/provider/planning/{s1,s2,s3}/{en,zh-CN}.md`。
- 系统提示 = 常驻 role law + 当前 stage 方法，都本地化。

```
    G4.3. 一次事务追加：

```

## §10 风险与取舍

1. **多 work 串号**：现状 `tryActiveWorkState` 取 map 头。多 plan session 会串。改按 session 解析（B4）。施工时先证。
2. **前缀稳定**：交接触发重锚。deliver 起的 Manager 是新 session，不污染 plan 的 epoch。
3. **review 泛化**：manager 的 review 深绑 relay。抽壳须保 manager 字节行为（E5）。
4. **provider-leak**：ask 的 LWR、deliver 的 execSessionId 不得进 provider 面。
5. **自然停止与 provider error 区分**：空停豁免，length/error 不豁免（I2）。
6. **只读软约束的代价**：DevOps 有 bash，只读仅提示词约束。真实越界不会被门拦。已知代价，记在案。
7. **SyncDelegate 无 DevOps**：需扩展 `SyncDelegateRole`，或复用 road-devops 派发。两选一。
8. **review 每任一次的持久化**：需 `Reviewed` 字段与事件；重放幂等。
