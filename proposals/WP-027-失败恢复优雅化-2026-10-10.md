# WP-027 失败恢复优雅化 · 取舍记录（2026-10-10）

## 用户可见行为表

只看重试预算、终态呈现、中止语义三件事，十一类失败收成五组：

1. ProviderTransient / ProviderPermanent：唯一能消耗重试预算的一组。
   条件齐（ProviderStarted × breaker Closed × 预算 Available × 可恢复 kind）才出
   RetryFreshAttempt；缺任一条件就地转 TerminalizeProviderStarted/Failed；呈现上
   retry 对应 Recovery，终态对应 Final。Transient 与 Permanent 的差异只在 breaker
   记哪一种失败，不影响用户可见行为。
2. UserCancelled / Superseded：中止语义。用户可见都是取消，不重试、不消耗预算，
   容量按 exact fence 释放。Superseded 与普通取消的差异在调用方（旧执行让路），
   不在失败策略内部。
3. ProtocolRejection / AuthorizationDenied：拒绝语义。终态 disposition 为 Rejected，
   不重试、不消耗预算。两者差异在调用方文案，不在策略。
4. LocalInvariant / CapacityQueueFull / StreamInterruptedAfterFirstToken：失败终态。
   行为完全一致：Terminalize + Failed + 释放 fence + 不重试。Fatality 只有
   LocalInvariant 一家是 FatalAfterSettlement，另两家是 NoFatality，这是唯一保留的差异。
5. AcceptanceUnknown / PersistenceFailure(NotCommitted|Committed|Unknown|NoNewWrite)：
   保持未知或保持现状。AcceptanceUnknown 与 PersistenceFailure(Unknown) 都走
   AwaitAcceptanceReconciliation；NotCommitted / Committed / NoNewWrite 都走
   PreserveCurrentFact；容量上前者 retain、后者按 lifecycle 释放；fatality 上只有
   Committed / Unknown / NoNewWrite 保留 FatalAfterSettlement。

## 筛掉的形式分支（四处，只并同行为分支，不删行为）

1. `releaseCapacity` 把四个 lifecycle × NoCapacityFence 的穷举并成一条通配。
   用户可见结论本来就一样：无 fence 就无结算。
   唯一保留的特例是 NoAcceptedFact × OwnsExactFence → 不结算（尚无可释放的已接纳执行）。
2. `retryProviderResolution` 把 Closed×Exhausted、Open×Available、Open×Exhausted
   三条并成一条通配。用户可见结论一样：只要预算或 breaker 缺其一，就地终态 Failed。
3. `decide` 把 AcceptanceUnknown 与 PersistenceFailure(Unknown) 并成一条，
   把 NotCommitted / Committed / NoNewWrite 并成一条。两组内部的用户可见行为本来就一致。
4. `PluginHostInterop.interpretHookFailure` 的 `decisionStillRequiresSettlement` 把
   13 条穷举收成三条语义谓词：retry 一律要结算；任一 terminalize 一律要结算；
   ReleaseExactFence 配任何决议都要结算；其余一律不要。逐条核对过，原 13 条里凡是
   判 true 的组合新谓词仍判 true，凡判 false 的仍判 false。

## 刻意保留的“刻板”

- 发送栅栏（provider-attempt-recovery-022 的 exact finalized errored assistant 投影）未动。
  它决定物理上能不能发第二个请求，是真行为，不是自洽。
- 容量结算（exact fence 的 No/Retain/Release 三态与 NoAcceptedFact 下不释放）未动。
  它决定资源归还给谁，是真行为，不是自洽。
- breaker 的 Transient / Permanent 区分未动。用户不可见差异，但它是 MJS 侧选路的
  真输入，删掉会丢信息。
- fatality 的 LocalInvariant / Committed / Unknown / NoNewWrite 四家 FatalAfterSettlement 未动。
  进程生死是真行为，不碰。
- 全部 ExecutionFailure 构造子未动。分类本身是 provider-attempt-recovery-019 的
  显式依据（哪些类别不花预算不重试），删类别会改契约，不属本卡“优雅化”范围。
