# 高效测试 Prompt

用于新写测试、补回归或优化既有测试。把下方模板交给测试 agent，填写任务目标即可；文件、入口和预算由 agent 从当前仓库核实。任务只要求提示词时生成实施 prompt；任务已经要求编写或优化测试时直接实施，不重复询问已明确的授权。

## 可直接使用的模板

你负责为当前任务设计成本合理、证据充分的测试。目标是保持有效行为覆盖，减少无效准备、重复计算和收尾等待。衡量结果时优先看用户实际运行范围的总耗时，不追求用例数量、断言数量或单个测试显示的低耗时。

任务输入：

- 任务目标：{要新增、修复或优化的行为}
- 模式：{生成实施 prompt；或实施，按当前任务选择}
- 范围与限制：{允许修改的模块、运行测试的资源限制；未指定则遵守当前任务约定}
- 已知证据：{需求条款、相关失败、耗时记录；没有则从仓库调查，不编造数字}

先阅读适用的 AGENTS、需求、真实实现和测试入口，检查工作区差异并保护无关改动。把下面的原则落实到本任务的具体文件、行为和验证方式。缺少的信息先从仓库和已有记录查找；未解决的合同分歧明确列出，不把当前实现直接当成正确答案。

### 选择足以证明行为的测试

明确每个测试要反驳的命题，再选择能证明它的最低成本边界。纯算法和业务时间推进可以使用合适的虚拟时钟；原生定时器销毁、事件循环退出、进程组回收、挂起与恢复等物理行为，需要对应的真实资源证据。不能用自建模拟器复刻被测算法，再用相同逻辑给它打分。

先让正常控制样本经过真实入口并完成预期效果，再加入受控违约。反例必须因目标缺陷失败，不能由缺依赖、错误权限、模块加载失败或任意异常代替。新增普通小测试不必附带全量性能实验；生命周期与优化回归要有能区分错误实现的正反例。

### 让资源随其所有者结束

列清测试及被测调用创建的 timer、listener、子进程、文件句柄、临时目录和后台任务：谁创建、谁持有、何时结束、如何证明释放。按真实合同覆盖正常完成、拒绝、同步抛错、异步失败、超时、取消，以及适用的挂起和恢复路径。

用 `finally`、`use` 或相应的作用域释放机制收束资源，并核对当前运行时的实际语义。资源创建后、第一次 await 前抛错也必须能清理。保留原始失败和清理失败，不能吞错取得绿色。只处理本次拥有的资源，不清理其他测试或用户进程。

`Promise.race` 不会自动取消输掉竞争的一方。分别判断等待用的 timer 是否已失效、后台工作是否仍应继续；挂起时可能需要保留程序与现场，却应结束本次等待。旧调用的回调不能干扰恢复后的调用。先排空或正确移交任务，再清空资源表。

不能靠 `unref`、强制退出、缩短产品预算或等兜底超时来伪装收尾成功。验证应观察资源真实销毁及相关进程自然结束；源码出现 `clearTimeout` 或 `Dispose`、进程退出，都不能单独证明资源已释放。资源观察限定于本次所有权和合同边界，不要求合法的后台工作或整个宿主的所有 timer 都归零。

生命周期优化至少同时证明两面：工作提前结束时没有遗留等待；工作仍未结束时，原来的超时、取消或自动挂起仍能生效。不要让清理优化误删必要的超时保护。

### 减少准备和无效等待

优先用就绪事件、握手、可控屏障或真实完成信号安排先后，避免固定 sleep 猜测状态。等待仍须有界；真实超时命题保留必要的真实时间，不改成零时延。涉及在途资源时，先证明工作确实在途，再触发取消或清理。

按准备、加载、执行、输出排空和退出回收分解成本。耗时接近某个固定预算、而 worker CPU 用时较少，是调查线索，不是泄漏结论。先定位仍存活的资源和所有者，再做局部修改；不要先提高并发或移动测试顺序。

昂贵且不可变的准备结果可在正确的版本、输入和隔离边界内复用。可变状态、权限、时钟、工作目录和资源所有权不能跨用例串用。不要为一点局部收益引入庞大的缓存或夹具框架；要把准备、失效和清理成本一并计算。

### 保持覆盖和运行环境可比

保留需求场景、有效断言、属性测试样本、种子及失败缩减。测试确需重构时，逐项说明旧义务由哪些新证据承接；新增回归单列，必要时放进前后两侧运行。未改测试可用内容摘要核对。文件数、用例总数或最终通过数相同，不能单独证明覆盖等价。

运行前核实实际工具版本、完整 PATH、依赖和会影响 skip 的能力。不要只固定 Node/npm 却漏掉测试依赖的 rg、Bun 等工具；依赖缺失使测试被跳过，不能成为提速证据。保留正式构建新鲜度检查，并验证聚焦入口实际选择了哪些文件。

比较真实发现集、完成集、启动用例身份、skip/TODO 身份和失败身份；确认结果流排空与所拥有进程的回收。崩溃、漏执行、额外跳过或环境变化的轮次不用于等覆盖的提速结论，完整保留记录并调查原因。不能只删除异常轮次，或反复重跑直到偶然变绿；未解释的可靠性变化单列为风险。

### 按任务范围验证收益

先跑相关 requirement 套件。只有任务要求优化整套，或改动影响全局运行机制时，再安排完整范围的前后对照。纯 prompt 或文档任务只检查内容与引用，不启动构建或测试。遵守已给出的资源限制和暂停要求；暂停时真正停止本次拥有的运行任务。

明确计时对象：完整 unit 的墙钟从正式 runner 启动到退出，包含 freshness、排空与回收；构建单列。若任务要求完整流水线，则按其真实阶段测量，不能用 unit 代替。不要将测试正文时间、worker 时间总和或 CPU 时间当成整套墙钟。

固定运行时、依赖、输入、并发、预算、运行层级与缓存条件；记录无法控制的负载。每轮内不修改被测输入。按波动补足必要的重复或交错对照，报告每轮值、汇总方法和排除理由。文件变快不等于整套变快，失败基线的耗时也不能外推为绿色流水线耗时。

### 交付可执行任务与可筛选记录

生成 prompt 时，直接输出针对本任务的实施 prompt，至少包含：

1. 需求目标、已知基线、允许修改与验证的范围。
2. 用例设计：输入与触发、可观察结果、正常控制、违约反例，以及必要的资源释放证据。
3. 实际文件与入口、准备复用边界、资源所有者和释放时机。
4. 分步实施与验证命令；需要确认的条件写成调查步骤，不编造路径、预算、基线或通过结果。
5. 如需性能对照，写清比较范围、等覆盖判定、环境预检、计时边界和无效轮次处理。
6. 记录要求：每项策略的原因、改动、前后数据、覆盖变化、失败与波动、保留或放弃决定，以及未验证边界。

生成 prompt 模式不实施改动或运行测试。实施模式按同一要求完成工作，输出实际证据并同步计划状态。局部验证、整套验收、提交推送和部署分别报告；不把局部成功写成整个计划已闭合。

## 本仓使用约定

模板适用于不同仓库，实际文件与命令必须从当前版本确认。在本仓，沿用 `requirements/<package>/tests/NNN.test.mjs` 与标题中的 `WHAT[PREFIX-NNN]` 归属规则。Fable 构建使用 `node scripts/build.mjs` 或正式验证入口，禁止 `dotnet build`。普通小变更先验证对应需求，不默认启动整套测试；提交和推送遵守本次任务已经确定的分支范围。

## 经验来源

参见[定时器优化记录](../evidence/test-optimization-20261027/README.md)与[测试优化计划](TEST-OPTIMIZATION-2026-10-24.md)。该次实验通过释放已结束调用的 yield 定时器，将本机完整 unit 有效对照的平均耗时从 315.0 秒降到 214.0 秒；有效行为覆盖未删减，仍有既有失败。32.1% 是该实验的观测值，不是模板的提速承诺。可复用的是资源所有权、正反例和等覆盖测量方法。
