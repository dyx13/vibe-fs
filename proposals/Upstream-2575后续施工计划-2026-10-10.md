### S0：把干净构建做成可交付的闭环

1. 在隔离的干净仓库中正式复现“无 dist、无 staged backup”的缺产物失败。已有产物的完整重建继续作为正控。
2. 依据 degeneration-guard [004]、verification-system [016] 裁决准备入口。现行 WHAT 同时要求手动更新、临时 runtime 产物、禁止 tracked 数值快照，不能直接把 normal/min/max 抄进源码。
3. 推荐最小方案是独立、显式的包络准备步骤，build 保持不派生、不检查语料变化。若该步骤要由 CI 自动执行，先在 WHAT 明确允许的发布准备边界并同步回归；这是合同裁决，不能把“显式”偷换成“手动”。若坚持人工派生，则先定义绑定源码输入的产物交付方式，CI 消费该产物，不依赖开发机 dist。
4. 验收包括干净首次准备+构建、已有产物重建保留、缺产物明确失败、正式 generated artifact 输入/输出绑定。跑 degeneration-guard [004] 与相关 verification [016]，再读新 SHA 的 CI。能进入下一阶段不等于 release 已通过。

### S1：先证明新合同真的穿过 Host

**S1a 退休链**：按 relay-assessment [001/004/005/008/010]、relay-retirement [005/007/008/009] 和 verification [014]。真实 Manager/HumanRoot 分别经过非空 findings→修复→后继独立评审、空 findings→末任清理；第一次 suicide 只有确认，第二次才退休；原资源收束、旧 attempt 中断完成后才 opening。

静态接手风险：`long-stroke.toml` 的 `humanroot-loop` 目前只声明 review 和一次 suicide；动态 binder 改了 findings，但没有给该 family 补第二次调用。这是候选缺口，尚未实际运行证明失败。先取正式红，按精确调用身份调整场景与 oracle，不凭追加一个 tool-call 就宣布完整链通过。

**S1b 待办消费**：按 attention-regulation [004—006]。现 `005.test.mjs` 的三角色用例直接调用投影 consume，不能单独证明自然终止入口实际呈现一次 user prompt。补 Manager 两段结束、Engineer/DevOps/Orchestrator 真终点、凭据落盘后新 OS 进程重放、同 occurrence 不复活及 life 隔离。拒绝不应伪造交付或新用户权威。

**S1c 用户通知**：按 concern-routing [003—006]。`003.test.mjs` 仍有实际 user 通知 TODO。从真实 publish 入口证明 live root 的 durable copy 与用户呈现、失败零假成功、stale generation 拒绝、重放/Pair Hint 边界；完成真实证明后再处理对应 TODO。

每个小包只跑对应 requirement 与必要相邻包。最终组合时用同一 OpenCode 进程的一次 Long Stroke；不同输入或分段补跑不能拼成整体绿。

### S2：分清存储成本和发布吞吐

- WP-023 采用当前 writer+内嵌 payload 输入，固定文件清单/hash、事件数/bytes、nowMs、Node/机器/source。分别量冷读、热读、追加后增量、同步、clean no-op 零 transport、争用后重取，并核完整 Current/载荷一致。旧 566MB 旁挂布局与旧 shard 数字不能充当现布局 A/B。
- 修前与修后的比较须同载荷协议；可用隔离的反向性能变异作对照并保正式正确性断言，不能直接将不同协议的两个 revision 的墙钟相减。证明不了的项目继续写未验证。正确性与协议回归进正式测试，成本表不是业务验收替身。
- S0 后冻结最终输入，实际运行原 release 入口，分别登记 unit/integration/harness/E2E/package 与资源组收据。若原 300 秒再截断，先取得同 PID CPU、父进程窗口、真实活动/排队与因果进展，定位可执行反例后才减冗余；不提高预算、降低并发或更换 tier 求绿。
- Homebrew Node26 复制缺库独立保留；明确选择可复制且依赖完整的受支持 runtime，阳性环境结果不撤销原平台失败。
