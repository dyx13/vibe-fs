- 前版记录：`proposals/W0-裁决-WP-012-底层id概念去除-2026-10-09.md`（偏简略，本版复核并细化实施范围）

## 盘点：id 种类与可见面

1. `SessionId`（Identity.fs:20）：Host 会话身份。内部职责面：`HandleRecord.ChildSessionId`（LinkageProjection.fs:44）、`tryFindByChildSession`（LinkageProjection.fs:671）、join/horizon 的 durable 关联键。provider 面禁词（leak-gate:42、49）。结论：职责 id，保留。
2. `AgentId`（Model.fs:49，`AgentRecord.AgentId: string`）：fork 运行时的进程内记录键。`HorizonTool.fs:178-179` 以它建 `runtimeByAgentId` 内部映射，但渲染只用 `labelForHandle` 的 Byname。provider 面禁词（leak-gate:43）。结论：内部键，保留；provider 面本来就不可见。
3. `HandleId`（Identity.fs:182-185，Agent/Pty/ManagerJob 三案联合）：join 邮箱与 linkage map 的键（`Map<HandleId, HandleRecord>`，LinkageProjection.fs:86）。`describe` 注明仅诊断渲染、永不解析回 fork 目标（Identity.fs:341-348）。结论：职责 id，保留。
4. `AgentHandleId`（Identity.fs:170、329-331）：`HandleId.Agent` 内层强类型，mailbox/ownership 的精确身份（`ICompletionMailbox<AgentHandleId,…>`）。结论：职责 id，保留；**严禁本次动它**（见下）。
5. `PtyId` / `PtyHandleId`（PtyTypes.fs:57-64；Identity.fs:173）：PTY 物理身份。horizon 的 pty 行只显示 command 或 terminal 名称（HorizonTool.fs:122-130），`JoinTool.fs:142-150` 同理。provider 面禁词（leak-gate:45、48）。结论：职责 id，保留。
6. `LaneIndex: int`（Fission Facts/Projection，`Map` 键与 merge 顺序）：fission 归并的内部序号。provider 面禁词 `lane_index`（leak-gate:50）。结论：内部归并键，保留。
7. `TerminalName: string`（`TryBindTerminalName` / `TryTerminalNameByPtyId`，PtyPort/Runtime）：provider 可见的 PTY 语义名（name→PtyId 映射的 name 一侧）。结论：语义身份，保留并作为显示用名。
8. `Byname: string`（LinkageProjection.fs:48）：provider 可见的逻辑人稳定名。`labelForHandle` 优先显示 Byname（HorizonTool.fs:73-75），`horizonVisible` 只决定哪些 handle 可见、从不暴露底层 id（610-621）。结论：语义身份，保留；它是替代底层 id 的显示方案，不是待删对象。

## 核对：现状

1. provider 面禁物理 token：`FORBIDDEN_TOKENS` 覆盖 `SessionId/AgentId/ManagerJobId/PtyId/FissionGroupId/agent_id/pty_id/session_id/lane_index`（leak-gate.mjs:41-51），扫描根含 HorizonTool、JoinTool、Tool、PtyTool 等 provider 渲染面（18-34），命中输出行即判违规（86-91）。
2. horizon 只显示 Byname 与 TerminalName：agent 行经 `labelForHandle`（Byname → TargetAgent 本名 → someone），pty 行经 command/terminal 名称；`runtimeByAgentId`、`record.PtyId` 排序都是内部键，不进文本。
3. ownership / attachment 需要物理身份：handle map 键、`ChildSessionId` 重绑、join 消费、忙闲归属（`OwnsAgent`）全依赖上述职责 id；`managed-session-lifecycle-015`（handle 即 Agent ID，重启仍绑同一子会话）与 EXEC-009 tombstone 语义都压在这些键上。

## 三问

1. 现状防住哪类真实错误？答：provider 面物理拓扑泄露——模型把 session/agent/pty id、lane 序号误认为可操作能力，或凭 id 猜测调度细节。
2. 去除后哪条 WHAT 条款失守？答：`participant-horizon-010`（仅 Byname/TerminalName 名册）、`delegation-005`（委托面不暴露机器拓扑）、`managed-session-lifecycle-006/008/015`（handle 四态、消费墓碑、身份稳定）、join/ownership 恢复链。
3. 更简单的实现？答：内部强类型一律不动；实施只做可见面核对与测试保护。若 gate 与名册测试全绿，本卡可零代码关闭。

## 结论

修改（收敛为可见面范围，不做内部强类型化）。

理由：七种标识中没有脚手架——`SessionId/HandleId/AgentHandleId/PtyId/LaneIndex` 是 ownership、join、恢复、归并的职责键；`Byname/TerminalName` 是替代底层 id 的语义显示名；`AgentId` 字符串只是运行时记录内键，provider 面本来不可见。provider 隔离已有禁词门与名册渲染双重保护。

## 实施范围（只给范围，不做强类型化）

1. 核对 provider 面：跑 `provider-leak-gate`，确认零违规；抽查 horizon/join 渲染输出只有 Byname / TerminalName / command 文本。
2. 若发现某处渲染直排底层 id（SessionId、AgentId、PtyId、lane_index），则改为 Byname/TerminalName 显示，内部键保持不动。
3. 测试保护：`participant-horizon/010、011`、`delegation/005、026`、`provider-leak-gate` 保持绿色；缺口才补断言，不为本卡新造内部类型测试。
4. 明确禁止：不动 `Identity.fs` 的任何强类型（`SessionId/AgentHandleId/PtyHandleId/ManagerJobId/HandleId` 及其 `describe/tryAgent`）；不动 `PtyId`、`LaneIndex` 内部键形态；不把 `AgentRecord.AgentId: string` 改为强类型。WP-012 曾因 `AgentHandleId` 半成品强类型化阻塞过，严禁重犯——本次任何涉及内部类型形状的改动都不在授权内，发现大改必要先回 Manager 另开卡。
5. 若核对全绿：零代码关闭本卡，记录即证据。

剩余边界：`AgentRecord.AgentId` 与 `AgentHandleId` 并存是已知的不一致（运行时 string 键 vs 强类型 handle），但收敛到一处属于强类型重构，已明确划出本次范围；后人若要动，另开实施卡并先过 Manager。
