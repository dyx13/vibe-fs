# 测试与验证规则

本文是 `verification-system` 的唯一规则正文，适用于本仓测试的编写、运行、优化和结果报告。先读本文，再读被测模块自己的业务合同；业务模块尚未迁移的 `WHAT.md` 和库侧局部 `AGENTS.md` 继续定义各自的行为。

既有 `WHAT[verification-system-NNN]` 测试锚点定位到下方同编号 SPEC，锚点名称不决定规范文件名。原 `WHAT.md` 仅保留导航。规范检查器直接读取本文，缺失时不得退回旧文件。构建和运行器执行代码，不会自动理解 Markdown；修改规则不等于修改实现或取得通过证据。

## AXIOM

1. **保护真实行为。** 使用者在乎承诺是否兑现，而不是测试显示了多少绿色。
   - 理由：不能暴露违约、没有到达实际边界或跟实现一起算错的测试，会让错误带着证明进入交付。
2. **结论可以复核。** 开发者需要知道哪份输入、哪些场景得到什么结果，以及哪里仍然未知。
   - 理由：省略失败、漏执行或混用版本，会让后续决定建立在不存在的成功上。
3. **验证成本值得支付。** 保留有效覆盖和可靠性，减少重复准备、无效等待及收尾成本。
   - 理由：开发者承担整次验证的等待与计算成本；降低测试数量或隐去失败不产生同等质量的收益。
4. **测试只管理自己拥有的资源。** 测试之间及测试与使用者的工作应互不干扰，合法的在途工作应有明确归属。
   - 理由：遗留定时器、任务和进程会拖慢或污染后续验证；随意清空共享资源又可能破坏正在进行的工作。

## LEMMA

### L1 — 按承诺选择最小充分边界

- 前提：AXIOM 1、3。
- 推理：纯计算、时间顺序和物理行为需要的观察不同。使用足以反驳目标命题的边界，才能既保持证据有效，又避免不必要的真实环境准备。只有共享同一生命周期本身是承诺时，才要求连续的真实场景。
- 适用条件：先确定被测合同与实际副作用。低层替身不能证明真实资源释放；局部通过不能替代完整发布。

### L2 — 判定依据独立且能够失败

- 前提：AXIOM 1、2。
- 推理：正常控制先证明入口和夹具成立，再由受控违约推翻目标承诺，才能排除缺依赖或任意异常造成的假反例。生成器若同时计算答案，或测试复刻业务状态机，就不能独立检验实现。
- 适用条件：断言覆盖合同要求的结果、顺序与副作用。人工才能判断的充分性和独立性保留人工审阅，不制造措辞扫描来代替。

### L3 — 结束等待与结束工作分别处理

- 前提：AXIOM 1、3、4。
- 推理：`Promise.race` 不会自动取消另一方；调用已经结束仍保留的定时器可能让整套测试等待原预算耗尽。作用域清理应收束本次拥有的失效资源，同时保留合同要求继续的工作及其保护。
- 适用条件：覆盖适用的成功、启动异常、异步失败、取消、超时、挂起与恢复。用 `finally`、`use` 等机制落实所有权；先排空或移交任务再清空记录，旧调用回调不能干扰恢复后的调用。不要求整个宿主或其他测试的资源归零。

### L4 — 因果和时钟各自提供证据

- 前提：AXIOM 1、3、4。
- 推理：固定 sleep 只能猜测状态；有界的事件、握手和屏障可以确定操作已经到达目标边界。逻辑时间用虚拟时钟重放，物理计时器、事件循环与进程回收用对应的真实观察。无关输出不能证明被监测目标仍在推进。
- 适用条件：真实超时行为保留必要的真实时间；不能把生产预算改为零或延长预算来取得绿色。等待与诊断都必须有界。

### L5 — 比较收益先保证比较对象一致

- 前提：AXIOM 2、3。
- 推理：环境缺失可能增加 skip，崩溃可能少运行用例，缓存可能掩盖陈旧产物。只有核对输入、工具能力、实际执行与排除身份，才能把耗时变化解释为等覆盖的改进。
- 适用条件：复用昂贵且不可变的准备时，以版本、输入及产物校验限定复用范围；不共享用例的可变状态、权限或资源所有权。重构保留有效义务并说明证据承接。

### L6 — 报告完整范围与完整成本

- 前提：AXIOM 2、3。
- 推理：正文完成、结果流排空和进程回收是不同事实。用户等待的是入口启动到结束的实际时间；worker 时间总和或 CPU 用时不能替代它。失败基线也不能证明绿色流水线的性能。
- 适用条件：先验证相关套件；任务要求整套提速或改动影响全局运行机制时再做完整对照。按波动安排必要重复，保留每轮、排除原因与尚未解释的可靠性变化。

### L7 — 门禁服务于可说明的违规

- 前提：AXIOM 1、2、3。
- 推理：空跑、机械行数和对某个内部写法的偏好不能证明承诺成立。检查器应命中真实对象，以同一实现接受合规替代方案并拒绝目标违约；工具异常必须如实失败。
- 适用条件：静态检查只覆盖它能识别的违规，不能声称由形式检查证明任意行为、oracle 独立性或全部测试覆盖。

## SPEC

### [001] 按承诺与副作用选择检查

前提：LEMMA L1。

检查层级由被验承诺与真实副作用决定，而非一条所有命题都必须逐级通过的固定阶梯：纯计算直接检查；需要时间确定性的部分使用虚拟时间；承诺真实环境行为的用真实组合检验。需要真实环境而场景互不依赖的承诺，可在独立环境中分别进行，不必共用单一环境。

### [002] Long Stroke 的生命周期范围

前提：LEMMA L1、L4。适用于需要共享物理生命周期的宿主验收。

Long Stroke 用于确实依赖同一共享生命周期的承诺，保持单一入口并在同一物理环境的单次生命周期内完成；相互独立的端到端场景不受此限，可在独立环境中并行进行。

### [003] 检查选择而非固定阶梯

前提：LEMMA L1、L6。

语义命题按承诺与实际副作用选择必要检查，不要求 Pure → Temporal → Adapter → Long Stroke 逐级通过，也不以“不适用须用户确认”作为通用门。局部范围内单独运行并如实报告其范围；not-run 与 failed 必须始终区分，失败不得改成通过。

### [004] verifier 必须可红

前提：LEMMA L2、L7。

所有测试必须能因所验证的要求被违反而失败。每个静态门禁必须有回归测试，以受控反例输入证明其能准确识别违约，并以非零退出码报告失败。严禁为使测试通过而削弱断言。

### [005] 中止

前提：LEMMA L2、L6、L7。

所有门禁、运行器与基础设施遇到数据损坏、协议失配、不可解析的边界状态或未知异常时，必须安全失败，并以非零退出码向上层报告；严禁吞没异常或报告通过。

就绪超时或就绪前退出不得计为验证通过。

### [006] 因果推进

前提：LEMMA L3、L4。

验证执行必须全程按距最近一次因果进展的静默时长判断挂死，首次进展前从监测开始计时；严禁仅以总运行时长判断。因果进展必须有受监测目标实际推进的证据，无关活动及同一进展的重复观察不得续期。

达到静默限值时，必须先输出因果诊断，再以非零退出码安全结束验证。诊断须说明受监测目标、当前等待及最近进展；无法取得的信息须标明缺失及原因，诊断采集不得无限阻塞退出。监测不得拖延验证正常结束。

### [007] Temporal

前提：LEMMA L1、L4。

Temporal 层测试必须基于虚拟时钟、可注入的时间端口与显式因果 trace，所有时间推进必须离散且可确切枚举。语义与逻辑证明严禁依赖真实 sleep 或物理时钟、调度的偶然性。

### [008] 断言与资源释放

前提：LEMMA L2、L3。

测试必须完整断言所验证命题要求的结果及副作用，不得以弱于要求的检查替代。规范规定精确结构或序列化文本时，必须完整比较。

测试与夹具应在自身生命周期结束时释放所拥有的资源；仍需运行的工作须有明确的所有权移交。正常结束、启动失败、异常、取消及超时等适用路径都要完成清理，清理失败不得吞没。资源生命周期的回归须同时证明已结束工作的资源真实释放，以及仍在进行的工作保留合同规定的保护；不能用强制退出或仅禁止资源保活代替释放。

### [009] 静态门禁命中真实路径

前提：LEMMA L5、L7。

静态门禁的扫描路径、目录匹配规则及检查入口必须对应真实存在的检查对象，严禁因目标不存在而空跑通过。

### [010] 验收判据不可放宽

前提：LEMMA L2、L5、L6。

未经正式规范修订，执行者不得放宽已冻结的验收判据、缩小验收范围，或将阻塞项降为不影响通过。删除冗余或失效断言不得削弱现行要求的有效保护。发布验收不得通过选择性采用重跑结果掩盖尚未解决的失败或不确定性。

等覆盖的耗时对照须保持需求场景、有效断言、属性测试样本、seed 与失败缩减能力一致；重构或新增回归单列并说明证据承接。减少覆盖、增加跳过或压低原有预算的结果，不得计作等覆盖提速。

### [011] 覆盖率门禁分母完整

前提：LEMMA L5、L7。

覆盖率分母必须涵盖全部项目生产模块，并与生产模块清单及当前编译产物核对一致；编译器运行库、外部依赖、测试和工具脚本不计入。未被测试加载的生产模块必须以 0% 覆盖率计入，严禁为填充分母而全量预加载模块，或擅自排除生产模块。

### [012] 禁止机械行数检查

前提：LEMMA L7。

门禁只针对明确的语义违规、架构越界或规范不变量破坏。严禁基于文件行数设置硬门禁或警告，严禁仅为证明政策存在而设立机械扫描门禁。

### [014] Long Stroke

前提：LEMMA L1、L4。本条承接主仓现存的 OpenCode 验收场景，不作为库侧所有测试都要经过的门槛；宿主场景的迁移须另行核对实际接线和未兑现的业务义务。

Long Stroke 必须在同一 OpenCode 进程的单次生命周期内，验证以下真实行为：

1. 嵌套 Replica 物理启动且不阻塞属主；
2. 伴生会话的前缀律、批次合并、会话删除捕获与结算；
3. 直接 HumanRoot Manager 循环的多轮迭代、权威消息继承与状态收敛；
4. 运行态 Join 屏障、无变更冷检索（Cold Fetch）与真实 Host 插件观测点。

### [015] 日志观察器因果消费与完整性

前提：LEMMA L2、L4、L6。适用于使用本仓 Journal Observer 取证的验证设施。

日志观察器（Journal Observer）只能将完整、合法的 `Fact` 记录识别为事实，不得根据正文关键字猜测。多字节 UTF-8 与未闭合行必须等待完整行结束符到达后，才能消费并提交位点。

非法 JSON、`event_id` 冲突、文件身份替换或已消费前缀截断必须报错。多写入者交错时仍须按日志顺序完整消费，位点单调前进，订阅通知与消费一致；关闭后停止监听与派发。日志的原子追加由 durable-events 的存储契约保证。

### [016] 验证输入版本与结果适用性

前提：LEMMA L5。

日常验证在当前工作树运行并记录其观察到的输入版本（运行前采集的输入摘要），阶段间重新采集输入并与起始摘要比较。输入中途变化时，后续阶段不再适用并以失败报告，已得结果只对变化前的输入版本成立；运行前是否发生变化无从观察，不得宣称“全程未变”。

稳定发布验证使用系统显式准备的源码产物完成构建与验证，与并行编辑隔离，其结论不受原工作树继续编辑影响。归档材料的路径逃逸与所有权校验始终保留；是否启用完整归档由具体交付需要决定，不是每次检查的前置条件。

前后耗时对照须记录并控制运行时、工具能力、依赖、输入、并发、预算、层级及缓存条件，保留产物新鲜度检查。核对实际发现、启动、完成的用例及 skip/TODO、失败身份；文件数或通过数相同不能单独证明执行范围一致。环境变化、崩溃或漏执行的轮次保留并调查，不用于等覆盖提速结论。

### [017] 日常与发布验证

前提：LEMMA L1、L6。以下入口层级描述本仓当前宿主验证，不替库侧构建与交付规则规定工具链。

日常验证执行格式、静态检查、构建、unit 与 integration；发布验证另加 Long Stroke 与打包证明。全量流水线是发布便利入口，不是唯一可接受的完成路径：可按受影响 requirement 运行聚焦套件并如实报告实际范围。not-run 与 failed 必须始终区分，任何失败都不得改成通过。

### [018] FCS 扫描禁令

前提：LEMMA L7。约束为扫描取证而启动或插桩编译器，不禁止编译工具为正常构建使用 FCS。

全仓禁止自建 FCS（`FSharp.Compiler.Service`）扫描，禁止为扫描取证额外启动或插桩编译器。

### [019] 测试行为与准备成本

前提：LEMMA L1、L2、L5。

尽量不使用扫描源码的测试，测试应该测试行为而非实现。

在保持验证边界的前提下复用昂贵的不可变准备，保留版本与输入校验；各用例的可变状态、权限、目录和资源所有权相互隔离。选择复用策略时计入准备、失效与清理成本，不为局部节省另建通用夹具或缓存框架。

### [020] 属性测试

前提：LEMMA L2、L5。

输入生成器只能构造合法输入、边界输入或明确非法的输入，不得计算预期结果；严禁在测试中重建状态机作为平行 oracle（预期结果的判定依据）。

无限或组合爆炸的输入域必须固定 seed、限定 run budget，并在失败时输出可重放的 shrink path；有限小域优先穷举。无法说明 oracle 独立性的随机测试不得宣称提供完整证明。

### [021] 验证范围与结论

前提：LEMMA L5、L6。

验证报告必须说明原定范围、实际完成范围及未完成原因，并区分被验对象违反要求与验证过程未取得有效结论。未执行、未取得有效结论及范围外事项不得计为通过；局部通过不得表述为整体验收通过。

耗时结论须对应实际验证范围，并计入该入口的准备、结果排空与资源回收。unit 与完整流水线分别报告，不以测试正文时间、CPU 用时或 worker 时间总和替代整套实际耗时。逐轮保留数据与排除原因，记录各策略的具体改动、覆盖变化、失败与波动及保留或放弃的依据；未解释的可靠性变化单列。

嵌套监督时，子进程 stdout/stderr 按 UTF-8 诊断文本经父进程转发，不能借继承的文件描述符或原始二进制块写入外层测试协议流。嵌入 node:test worker 时，其 stdout 专用于原生结果协议，子进程的诊断转发到 stderr；普通独立命令仍保留 stdout/stderr 的区分。文本解码必须保留跨块的合法多字节字符；非法 UTF-8 可显示替换字符，不宣称诊断文本是原始二进制存档。输出中即使出现类似协议头的字节，也不得被解释为测试结论；权威结果仍只来自独立 IPC 通道及其完整收尾证据。
